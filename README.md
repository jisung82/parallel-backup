# Parallel Backup

현재 버전: **1.6.3**

Windows에서 사용하는 GUI 기반 병렬 백업 프로그램입니다.

## 핵심 기능

### 병렬 백업
- 하나의 원본 폴더를 여러 경로에 동시에 백업
- 대상별 병렬도 제한
- 대상 수가 많아도 설정한 worker 수만큼만 동시에 실행

### 이름/ZIP 스냅샷
- 백업 이름 + 날짜/시간 자동 생성
- 같은 초에 여러 번 실행해도 `_01`, `_02` 식으로 충돌 회피
- ZIP은 첫 번째 백업 대상에서 직접 생성하며 시스템 TEMP에 전체 staging을 만들지 않음
- 생성 중 ZIP은 `.parallel-backup-build-*.zip.partial`로 작성
- 대상 복사 중에는 `.parallel-backup.partial-*.zip`을 사용
- 검증 성공 후에만 최종 ZIP 이름으로 원자적으로 확정

### 증분 백업
- 각 대상 경로의 최근 **검증 완료 ZIP**을 기준으로 비교
- 변경되지 않은 파일은 이전 검증 ZIP에서 직접 재사용
- 이전 버전(v2) manifest도 증분 기준으로 호환

### SHA-256 무결성
- 정밀 검사 백업에서 원본/ZIP/복구 대상의 파일 내용을 SHA-256으로 검증
- 누락/변조/복사 오류를 탐지
- 검증 완료 ZIP만 이후 증분 백업의 기준으로 사용
- 복구 후에도 SHA-256 재검증


### ZIP 아카이브 자동 생성
- 검증된 ZIP을 각 백업 대상에 저장
- ZIP 내부에도 `.parallel-backup/manifest.json`을 포함
- 생성된 ZIP의 CRC를 검증하고, 정밀 모드에서는 파일별 SHA-256도 검증한 뒤 최종 ZIP으로 확정
- 기존 검증 ZIP은 다음 증분 백업의 기준으로 유지
- 오래된 검증 ZIP은 보존 정책에 따라 삭제

### 정밀 검사 원칙
- 정밀 검사 모드에서는 파일별 SHA-256을 매번 실제 계산
- 이전 메타데이터만으로 SHA-256을 재사용하지 않음
- 취소 요청은 원본 스캔/해시 계산/ZIP 생성/검증에 전달됨


### 제외 패턴
쉼표 또는 줄바꿈으로 패턴을 지정할 수 있습니다.

예:

```
.git
Library
Temp
*.log
*.tmp
node_modules
```

파일명뿐 아니라 상대 경로 기준 패턴도 처리합니다.

### 디스크 사전 검사
현재 ZIP 백업은 전체 스냅샷으로 생성됩니다. 첫 대상은 압축 파일을 직접 스트리밍 생성하며, 실제 사용량은 압축 결과에 따라 달라집니다. 최악의 원본 크기 기반 공간 추정은 경고로 제공하고, 최소 안전 여유공간을 확보하지 못하면 시작하지 않습니다. 다른 대상은 ZIP 실제 크기를 기준으로 사전 용량 검사합니다.

### 보존 정책
대상별로 최신 N개의 **검증 완료** 스냅샷을 유지하고 오래된 스냅샷은 자동 삭제합니다.

### 장애 대응
- 24시간 이상 남아 있는 중간 `.partial` 폴더 자동 정리
- 검증 실패/취소된 ZIP은 증분 기준으로 사용하지 않음
- 작업 중 취소 가능

### 설정 프로필
설정은 자동 저장됩니다.

```
%LOCALAPPDATA%\ParallelBackup\profile.json
```

저장 항목:
- 원본
- 백업 이름
- 백업 대상
- 증분/검증 옵션
- 병렬도
- 보존 개수
- 제외 패턴

## 실행

Python 3.10 이상 권장.

```powershell
python app.py
```

또는 `ParallelBackup.bat`를 실행할 수 있습니다. 두 실행 경로는 동일한 백업 엔진을 사용합니다.

외부 Python 패키지는 필요하지 않습니다.

## 예시

원본:

```
C:\ai\uni_mcp
```

이름:

```
uni_mcp
```

대상:

```
D:\Backups
E:\Backups
F:\Backups
```

D:\Backups\uni_mcp_20260921_193000\
D:\Backups\uni_mcp_20260921_193000.zip

## 권장 설정

대형 개발 프로젝트에는 보통 다음 구성이 적합합니다.

```
증분 백업       ON
SHA-256 검증    ON
동시 대상 수    2~4
보존 스냅샷     5~10
```


## 주의

- 백업 대상은 원본 폴더 내부에 두지 마세요.
- 복구 시 ZIP/manifest 경로는 대상 폴더 밖으로 탈출할 수 없도록 검증합니다.
- 중요한 데이터는 서로 다른 물리 드라이브 또는 다른 저장 위치에 복수 백업하는 것을 권장합니다.

## 1.6.2 Hardening

- 시스템 TEMP에 원본 전체를 staging하지 않습니다.
- 첫 번째 백업 대상에서 ZIP을 직접 구성합니다.
- ZIP 누락/추가 멤버, 중복 이름, CRC 오류를 검사합니다.
- 정밀 모드에서는 파일별 SHA-256과 대상 ZIP SHA-256을 검증합니다.
- 복구 시 ZIP 및 manifest 경로 탈출을 차단합니다.
- 작업 취소는 원본 스캔, 해시 계산, ZIP 생성, ZIP 검증 및 복사에 전달됩니다.
- 자동 업데이트는 app.py, ParallelBackup.bat, parallel_backup_launcher.py를 함께 교체합니다.


## 1.6.3 — 저장공간·정지 안전성 정밀 감사

- **저장 위치**: 첫 번째 대상에 `.parallel-backup-build-*.zip.partial`을 생성하고 검증합니다. 추가 대상에는 `.parallel-backup.partial-*.zip`을 임시 생성하며 검증한 뒤 최종 `<백업이름>.zip`으로 이름을 바꿉니다. 첫 번째 대상의 ZIP은 **다른 대상 복사가 끝난 뒤 마지막에 원자적 이름 변경**하므로 동시 복사 중 원본이 사라지지 않습니다.
- **Windows 시스템 TEMP에는 대용량 staging을 새로 만들지 않습니다.** 이전 버전의 `%TEMP%\\parallel-backup-stage-*`, `%TEMP%\\parallel-backup-master-*.zip`은 남아 있을 수 있으며 자동 삭제하지 않습니다.
- **증분의 의미**: 기존 ZIP에서 변경되지 않은 파일을 읽어 원본 I/O를 줄일 수 있지만 **신규 스냅샷은 여전히 완전한 ZIP**입니다. 델타 보관/블록 단위 중복제거는 없습니다. 용량은 대략 `각 ZIP 크기 × 대상 개수 × 보존 개수`까지 늘어날 수 있습니다.
- **보존 정책**: 검증 완료된 ZIP만 최신 N개 유지합니다. 정상 백업 후 과거 ZIP 삭제 용량을 기록합니다. 과거의 .partial 잔여물은 일정 시간 뒤 정리하며 해당 바이트 수도 기록합니다.
- **중간 실패/정지**: 대상 ZIP은 검증 후 최종 파일명으로 확정합니다. 쓰기 실패나 정지 시 .partial 삭제를 시도하고 경로/회수한 바이트/실패 원인을 로그에 기록합니다. 복구도 파일 **하나씩** 동일 폴더에 임시파일로 기록 후 검증하여 교체하므로 복구 도중 정지하더라도 기존 파일을 중간 내용으로 덮어쓰지 않습니다. 강제 프로세스 종료나 전원 차단은 정리 코드를 실행할 수 없어 잔여물이 남을 수 있습니다.
- **파일 검증**: ZIP CRC/크기/manifest/파일별 SHA-256(정밀 모드)을 검사하며, 중복 압축 해제 패스를 줄였습니다. 정밀 모드에서 각 대상 ZIP은 원본 마스터 ZIP의 SHA-256과 비교합니다.
- **정밀 로그**: `%LOCALAPPDATA%\\ParallelBackup\\logs\\` 폴더에 실행별로 저장합니다. 로그당 약 8MiB, 최근 20개/총 32MiB 제한(정리 시점은 다음 로그 세션 시작). GUI에도 주요 작업 단계가 표시되며 오류 스택과 partial 경로가 남습니다.
- **공간 진단**: 프로젝트 디렉터리에서 `py -3 storage_report.py`를 실행하면 저장된 대상의 ZIP/잔여 임시파일과 이전 TEMP 잔여물을 보여줍니다. `py -3 storage_report.py --deep`은 큰 임시 **폴더의 실제 크기**까지 측정하지만 오래 걸릴 수 있습니다. 어떤 파일도 삭제하지 않습니다.
- **실제 검증**: Windows GitHub Actions의 작은 파일/3대상 병렬 복사, 일반·정밀 ZIP 검증, 디스크 가득 참/취소/검증 오류 유도, 정지 중 복구 대상 보존 등을 테스트합니다. 실제 사용자의 20만 개 이상 파일/여러 물리 디스크 E2E는 별도로 실행해야 합니다.
